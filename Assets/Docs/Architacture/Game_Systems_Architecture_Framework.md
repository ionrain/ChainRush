# Game Systems Architecture Framework

*(Стандарт архитектуры игровых систем)*

------------------------------------------------------------------------

## 1. Назначение и область применения (Purpose & Scope)

Данный документ описывает стандарт построения архитектуры игровых
проектов студии.

Он применим к:

-   realtime играм (RTS, ARPG, survivors-like)
-   пошаговым играм (turn-based strategy)
-   симуляторам
-   мобильным F2P проектам
-   сервисным играм (live-service)
-   синглплеерным и мультиплеерным проектам

Документ определяет:

-   архитектурную модель (Architectural Model)
-   базовые контракты (Core Contracts)
-   правила зависимостей (Dependency Rules)
-   принципы расширяемости (Extensibility Principles)
-   место системы оркестрации (Decision & Orchestration Platform)

------------------------------------------------------------------------

# 2. Базовая архитектурная модель (Core Architectural Model)

Архитектура построена вокруг строгого разделения:

-   Состояние мира (World State)
-   Правила изменения состояния (Rules)
-   Принятие решений (Decision Making)
-   Исполнение (Execution)
-   Представление (Presentation)

------------------------------------------------------------------------

## 2.1. Слоевая модель (Layer Model)

### 1. Модель мира (World Model)

-   хранение состояния (State Storage)
-   сущности (Entities)
-   компоненты (Components)
-   индексы и запросы (Queries)

Изменение состояния разрешено только через команды (Commands).

------------------------------------------------------------------------

### 2. Наблюдение (Sensing Layer)

-   сбор фактов из мира
-   вычисление производных данных
-   формирование снимков (Snapshots)

Sensing не принимает решений.

------------------------------------------------------------------------

### 3. Формирование намерений (Proposal Layer)

-   системы генерируют предложения действий (Proposals)
-   игрок, AI, сценарии, директор спавна, экономика и др.

Proposal не изменяет состояние напрямую.

------------------------------------------------------------------------

### 4. Арбитраж (Arbitration Layer)

-   выбор одного или нескольких предложений
-   применение приоритетов (Priority)
-   оценка (Scoring)
-   бюджеты (Budgets)
-   блокировки (Locks / Commit Windows)

------------------------------------------------------------------------

### 5. Исполнение (Execution Layer)

-   преобразование решений (Decisions) в команды (Commands)
-   изменение состояния
-   публикация доменных событий (Domain Events)

------------------------------------------------------------------------

### 6. Представление (Presentation Layer)

-   UI
-   анимация
-   VFX
-   звук
-   визуальные эффекты

Presentation не влияет напрямую на правила.

------------------------------------------------------------------------

# 3. Базовые контракты (Core Contracts)

Следующие контракты считаются инвариантами архитектуры и не должны
изменяться от проекта к проекту.

------------------------------------------------------------------------

## 3.1. Состояние и запросы

-   `IWorldState` --- внутреннее состояние
-   `IWorldQuery` --- только чтение (read-only access)
-   `WorldSnapshot` --- неизменяемый снимок (immutable snapshot)

------------------------------------------------------------------------

## 3.2. Намерения и решения

-   `Proposal` --- предложение действия
-   `Decision` --- результат арбитража
-   `IProposalSource` --- источник предложений
-   `IArbiter` --- механизм выбора

------------------------------------------------------------------------

## 3.3. Команды и события

-   `ICommand` --- атомарное изменение состояния
-   `IDomainEvent` --- факт изменения
-   `ICommandBus` --- шина команд
-   `IEventBus` --- шина событий

------------------------------------------------------------------------

## 3.4. Данные и контент

-   `ContentId`
-   `BalanceConfig`
-   таблицы (Data Tables)
-   версии схем (Schema Versioning)

Контент должен быть data-driven.

------------------------------------------------------------------------

# 4. Платформа принятия решений (Decision & Orchestration Platform)

Данный раздел описывает систему оркестрации.

Подробная спецификация содержится в:

> Orchestration_Architecture_Charter

Оркестрация отвечает за:

1.  Сбор предложений (Collect Proposals)
2.  Арбитраж (Arbitrate)
3.  Исполнение решений (Execute Decisions)
4.  Публикацию событий
5.  Управление циклом выполнения (Scheduler)

Оркестрация не содержит бизнес-логики конкретных систем.

------------------------------------------------------------------------

# 5. Руководство по построению доменных систем (Domain System Guidelines)

Каждая игровая система должна:

1.  Работать через Proposals и Commands.
2.  Читать мир только через `IWorldQuery`.
3.  Не иметь прямых зависимостей на другие доменные системы.
4.  Не зависеть от UI или движка.

Примеры доменных систем:

-   Combat System
-   AI System
-   Movement System
-   Economy System
-   Spawn Director
-   Objectives / Quests
-   Progression
-   Turn System
-   Inventory
-   Loot

------------------------------------------------------------------------

# 6. Правила зависимостей (Dependency Rules)

Архитектура должна быть ациклической (Directed Acyclic Graph).

Разрешено:

-   Domain → Core Contracts
-   Integration → Domain
-   Presentation → Domain Events

Запрещено:

-   Domain → Integration
-   Domain → Presentation
-   Cross-domain direct calls
-   Мутация состояния вне Command pipeline

------------------------------------------------------------------------

# 7. Расширяемость и адаптация под жанр (Genre Adaptation Strategy)

Архитектура должна поддерживать:

-   Realtime Scheduler
-   Turn-Based Scheduler
-   Deterministic Mode
-   Multiplayer Replication
-   LiveOps / Remote Config

Изменяются: - Policy арбитража - Набор proposal sources - Набор
executors - Данные

Не изменяются: - Core Contracts - Command discipline - World separation

------------------------------------------------------------------------

# 8. Инварианты архитектуры (Architectural Invariants)

1.  Состояние изменяется только командами.
2.  Решения принимаются только через арбитраж.
3.  UI не содержит правил.
4.  Формулы не находятся в Presentation.
5.  Контент не зашивается в код.
6.  Все зависимости контролируются на уровне модулей.

------------------------------------------------------------------------

# 9. Анти-паттерны (Anti-Patterns)

Запрещено:

-   God Manager
-   Прямые вызовы между системами
-   Логика в MonoBehaviour без доменного слоя
-   UI как источник истины
-   Побочные эффекты вне Command pipeline
-   Распределённая логика формул

------------------------------------------------------------------------

# 10. Версионирование и эволюция (Versioning & Evolution)

Любая система должна:

-   поддерживать миграции состояния
-   иметь версию схемы
-   быть расширяемой без переписывания контрактов
