# Orchestration Architecture Charter

*(Спецификация платформы принятия решений в рамках Game Systems
Architecture Framework)*

------------------------------------------------------------------------

## 1. Назначение и область ответственности (Purpose & Responsibility)

Данный документ является подразделом:

> Game Systems Architecture Framework

Он описывает реализацию **Платформы принятия решений (Decision &
Orchestration Platform)** в рамках базовой архитектурной модели (Core
Architectural Model).

Оркестрация:

-   не является Моделью мира (World Model),
-   не является доменной системой (Domain System),
-   не относится к слою представления (Presentation Layer),
-   не содержит бизнес-логики конкретных игровых механик.

Оркестрация реализует координацию слоёв:

-   Proposal Layer\
-   Arbitration Layer\
-   Execution Layer

в соответствии с Core Contracts.

------------------------------------------------------------------------

# 2. Архитектурная позиция (Architectural Position)

Оркестрация функционирует поверх следующих неизменяемых контрактов (Core
Contracts):

-   `Proposal`
-   `Decision`
-   `ICommand`
-   `IDomainEvent`
-   `IWorldQuery`
-   `WorldSnapshot`

Оркестрация не изменяет состояние напрямую и не хранит состояние мира.

Изменение состояния возможно только через Command pipeline в
соответствии с Architectural Invariants.

------------------------------------------------------------------------

# 3. Цикл принятия решений (Decision Loop)

Оркестрация реализует единый цикл:

1.  Получение неизменяемого снимка мира (`WorldSnapshot`)
2.  Сбор предложений от всех зарегистрированных `IProposalSource`
3.  Передача списка `Proposal` в `IArbiter`
4.  Получение `Decision`
5.  Передача решения в Execution Layer через `ICommandBus`
6.  Применение `ICommand`
7.  Публикация `IDomainEvent`

Оркестрация не принимает решений самостоятельно.\
Она делегирует выбор `Decision` механизму `IArbiter`.

------------------------------------------------------------------------

# 4. Scheduler Model

В рамках Genre Adaptation Strategy оркестрация должна поддерживать:

-   Realtime Scheduler
-   Turn-Based Scheduler
-   Event-Driven Scheduler
-   Deterministic Mode

Тип Scheduler не влияет на Core Contracts и не изменяет дисциплину
Command pipeline.

------------------------------------------------------------------------

# 5. Контракты оркестрации (Orchestration Contracts)

## 5.1. IProposalSource

Источник предложений обязан:

-   работать только на основе `WorldSnapshot`
-   не изменять состояние (`IWorldState`)
-   не вызывать `ICommandBus`
-   быть детерминированным при одинаковом Snapshot

------------------------------------------------------------------------

## 5.2. IArbiter

Арбитр обязан:

-   принимать только список `Proposal`
-   формировать `Decision`
-   не обращаться к Integration Layer
-   не выполнять команды напрямую
-   быть заменяемым (pluggable policy)

Политика арбитража (Policy) может быть:

-   Priority-based
-   Score-based
-   Budget-based
-   Lock / Commit-based
-   Hybrid

Политика не должна зависеть от конкретных доменных реализаций.

------------------------------------------------------------------------

## 5.3. Execution Integration

Execution Layer:

-   принимает `Decision`
-   преобразует его в `ICommand`
-   отправляет команды в Command pipeline
-   публикует `IDomainEvent`

Execution не принимает решений и не изменяет архитектурные правила.

------------------------------------------------------------------------

# 6. Инварианты (Architectural Invariants)

Оркестрация обязана соблюдать инварианты Framework:

1.  Состояние изменяется только через `ICommand`.
2.  Решения формируются только через `IArbiter`.
3.  Оркестрация не содержит бизнес-состояния мира.
4.  Оркестрация не зависит от Presentation Layer.
5.  Оркестрация не зависит от Integration Layer.
6.  Все зависимости остаются ациклическими (Directed Acyclic Graph).

------------------------------------------------------------------------

# 7. Расширяемость (Extensibility)

Оркестрация должна позволять:

-   подключать новые `IProposalSource`
-   заменять `IArbiter`
-   добавлять middleware (логирование, профилирование, телеметрия)
-   адаптировать Scheduler

Без изменения Core Contracts и без нарушения Dependency Rules.

------------------------------------------------------------------------

# 8. Запрещённые практики (Anti-Patterns)

В рамках оркестрации запрещено:

-   обходить Arbitration Layer
-   вызывать доменные системы напрямую
-   изменять состояние вне Command pipeline
-   хранить данные мира внутри оркестрации
-   внедрять UI- или Engine-зависимости

------------------------------------------------------------------------

# 9. Версионирование и эволюция (Versioning & Evolution)

Изменения в оркестрации:

-   не должны требовать изменения Core Contracts
-   не должны нарушать Architectural Invariants
-   не должны требовать переписывания доменных систем
-   должны сопровождаться версией документа

------------------------------------------------------------------------
