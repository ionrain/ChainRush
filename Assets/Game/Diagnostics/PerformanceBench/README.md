# PerformanceBench

Статус реализации: **working model** для сценариев стенда, **minimum seam** для измерительной интеграции общего пакета. Стенд предназначен только для ChainRush в Editor.

По решению от 2026-10-19 обе Activity стенда выполняют максимум один полный шаг симуляции за кадр (`Budgeted`, `maxStepsPerFrame=1`). Номинальный интервал сохраняется: 1/30 секунды. Расчёты, commits, синхронные слушатели и обратные результаты завершаются внутри этого шага; они не распределяются между последующими кадрами. Существующий планировщик сохраняет отставание часов без сброса.

Текущая производительная цель — **средний полный шаг в режиме Normal ≤7,6 мс** (`meanCompleteStepMs`). Вся подготовка текущего шага входит в его стоимость. Полный кадр, кадры без симуляции и фактическая частота показываются отдельно. Новая конфигурация лимита не объявляется ускорением вычислений; старые захваты с лимитом четыре шага за кадр сохраняются со своими исходными условиями.

### Физическая подготовка по необходимости

working model: исходная физическая поза и ревизии хранятся один раз на intent. Пакетная job параллельно ограничивает только непрерывные точки; действующий предварительный Yield пропускает эту работу. Геометрия и регистрация физической координаты выполняются для рассматриваемой точки, проекция на маршрут — после успешной live-проверки Spatial. Нулевой шаг сохраняет прежнюю проверку progress. Callback может возобновить пропущенный диапазон в том же pump; его scores используют исходный снимок соседей, физика — актуальную позу.

Новые физические координаты регистрируются в порядке фактического обращения. Их номера и выбор при равных вариантах могут отличаться от прежней реализации; существующие handles и Entity-цели сохраняются. Подготовка steering-кандидатов и Swarm не отключается.

minimum seam: SkillsSummary сохраняет `movementEvidence.population` для всей популяции на всех наблюдаемых шагах, включая Entity без запросов. `Moving`, `YieldOnly`, `Blocked`, `Other` — взаимоисключающие группы по фактическому результату шага. Два противоположных принятых перемещения считаются движением; `Waiting` не означает физическую неподвижность. Расстояние в population — сумма непрерывных смещений в координатах Unity. Показываются серии неподвижности, реальная работа и inclusive wall time Resolve; worker CPU не распределяется между группами по счётчикам.

Раздельные этапы физики: общие входы, ограничение, геометрия, регистрация, проекция, live-проверка, применение и обратные ответы. Вложенные времена не суммируются. Normal не включает подробный сбор. Сравнение использует исправленный baseline и кандидата с одинаковым лимитом один шаг за кадр; прежние 32,82/60,59 мс не подменяют новые измерения. Точная причинная цена исправления относительно ошибочного движения отдельно не установлена.

Сцена: `Assets/Game/Scenes/Diagnostics/PerformanceBench.unity`. Открывать её самостоятельно, без дополнительно загруженных игровых сцен. Для Addressables требуется **Play Mode Script → Use Asset Database (fastest)**. Защитный обработчик сообщает об этом требовании, но сам настройку не меняет. Deep Profile должен быть выключен.

## Управление

Пять режимов: Lifecycle, AI + movement, AI + navigation, Render control, Churn + movement. Start фиксирует параметры формы на один запуск; Run selected series выполняет только отмеченные строки, с указанным количеством повторений. Add current settings to series добавляет собственную комбинацию без автоматического выбора. Оценка длительности включает прогрев и измерение; подготовка и очистка добавляют время.

Create batch / Delete batch работают в измеряемом этапе, после завершения предыдущего пакета. Stop и Clear прекращают новые команды, завершают принятую работу и закрывают Activity. Итог прерванного запуска отмечается отдельно. Export записывает сводку завершённых запусков; покадровые данные каждого запуска сохраняются автоматически после очистки.

В Lifecycle время жизни отсчитывается после готовности всего пакета. Интервал начинается после завершения удаления. В Churn очередная замена начинается после удаления и восстановления популяции, затем выдерживается интервал. Пакеты состоят из отдельных экономических операций.

Повторный выпуск в Churn сначала пробует исходное место, затем до 63 точек в той же области, определённых seed, номером объекта и его жизни. Свободное место выбирает штатное пространственное резервирование; маркер создаётся только после успешного резерва. Исчерпание вариантов завершает запуск с ошибкой и штатной очисткой. Начальное размещение остальных режимов сохранено. Число попыток и стоимость подготовки записываются отдельно в operations.csv.

Начальная популяция подготавливается пакетами по 25 объектов: следующий пакет принимается только после готовности предыдущего. Это ограничение действует до прогрева и не меняет измеряемые пакеты, частоту нагрузки или бюджеты сервисов.

Кадры перехода между этапами сохраняются с phaseBoundary=true и исключаются из сводки измерения: их полная длительность может включать последующее сохранение профиля или очистку. Остальные кадры, включая обычный GC, остаются в среднем.

Если backend не предоставляет GC.GetAllocatedBytesForCurrentThread, байты отдельной операции и пакета обозначаются -1, а причина записывается в counter-availability.txt. Покадровый GC.Allocated и allocation samples профайлера остаются отдельными источниками данных; нулевой ответ неподдерживаемого API не выдаётся за отсутствие выделений.

В режимах AI и Churn используются прямые маршруты. Все движущиеся объекты сохраняют MobileSolid и штатный traffic: Movement требует эффективного occupancy-состояния. Navigation дополнительно использует AStar и препятствия. Обе нагрузки имеют независимые бюджеты 64 и Population. Разница режимов включает весь их состав. Плотность меняет размещение; слишком плотная конфигурация может быть отклонена штатной проверкой размещения и должна завершиться неуспешным результатом.

Warm подготавливает всю ёмкость пула перед измерением. Expansion начинает с заданной малой ёмкости. Для постоянной популяции первоначальное расширение происходит при подготовке; его данные остаются в CSV соответствующего этапа. Для измерения расширения использовать Lifecycle с пакетом больше начальной ёмкости. Первый пробный выпуск и удаление выполняются вне измерения и прогревают загрузку prefab и основные пути регистрации.

## Existing System Fit

Runtime стенда владеет командами, стадиями, учётом и результатами. Время остаётся у GameRuntimeHost, LocalRealtimeDriver и Scheduling. Token выпускает и удаляет EconomyService; материализацию выполняют ActivityService и CapabilityHostService; Entity и capabilities очищают их штатные владельцы. Projection и существующий пул владеют представлением. AI orders адресованы Entity; Skills, Movement, Navigation и traffic выполняют перемещение. Transform объектов стенд не перемещает.

У Activity одна команда с существующим PlayerKnowledge: производные ресурсные данные обслуживаются штатными Knowledge handlers. Каталог самостоятельного профиля содержит десять необходимых ресурсов и определений; размер фактически установленного каталога записывается в environment.json. Данные игровых захватов не являются эквивалентной нагрузкой этого профиля. Игровые цели, производство, волны, боевые правила, Board/Experience UI и MorbooFramework находятся вне стенда.

Цели маршрута, препятствия и временные маркеры размещения учитываются отдельно от популяции. Новая жизнь pooled view получает новую Entity; отложенные patrol-команды проверяют Activity, Run и Life. Обработчики projection lifecycle проверяют полный handle при удалении представления.

## Результаты

Папка: `ProfilerCaptures/PerformanceBench/<UTC>_normal|trace_run-<Run>`.

- frames.csv — все записанные кадры всех стадий. Статистика summary.json использует только Measuring; обычный GC остаётся во времени кадра.
- operations.csv — каждая завершённая либо неуспешная операция, handle/epoch, Entity, Token, стадия принятия, время принятия/появления/готовности/удаления/освобождения view.
- batches.csv — запрошенное количество, записанные и успешные операции, наблюдённые CPU/аллокации и задержка завершения пакета.
- summary.json — среднее, медиана, p95/p99/max, кадры с шагом и без шага, частота симуляции, запрошенная и фактическая нагрузка, маршруты, очередь, движение и occupancy.
- environment.json / phases.json — Unity, ревизии и dirty-состояние, MVID, Game View, ограничения времени, Profiler, правила учёта и границы стадий.
- counter-availability.txt — доступность счётчиков. Значение −1 обозначает недоступные данные. Переполнение любого буфера завершает запуск с неполными данными.

CPU/аллокации операции охватывают принятие, работу штатного журнала экономики и синхронную материализацию. Работа вспомогательного размещения вынесена в helper-поля. Расходы закрытия handle, общей очереди и отложенной привязки view не доступны как полное время отдельного объекта. Они остаются в кадре и иерархии профайлера. Наблюдённое время нельзя выдавать за полный CPU всего lifecycle.

Inclusive counters вложены друг в друга; складывать их нельзя. Полную разбивку приложения, Editor и Profiler получать существующим MorbooProfilerCaptureDumpTool. Его диагностические JSON кадров теперь сохраняют непрозрачный workloadContext с Run, Phase, Activity и параметрами; общий пакет не знает типы стенда. PerformanceBench.Work, Observe и PlacementHelpers выделяют работу стенда. Проверки occupancy и подсчёт видимых объектов выполняются дважды в секунду. Неподтверждённые причины обозначать **cause not established**.

## Подготовленные проверки — без выполнения

Тесты, Play Mode и захваты требуют отдельного разрешения после завершения всей реализации. Проверка компиляции не подтверждает выполнение нагрузки.

EditMode: параметры без автоматического исправления, повторяемое размещение, фиксация явно выбранной серии, ручное завершение Activity, отсутствие сцены в игровых сборках, границы фаз и полный экспорт кадров.

PlayMode: повторная выдача view новой Entity и позднее удаление старой привязки; остановка во время создания; четыре постоянных сценария при двух бюджетах, включая наблюдение движения вне камеры; расширение пула отдельно от прогретого состояния.

После разрешения дополнительно пройти сценарии:

| Случай | Наблюдаемое условие |
|---|---|
| 5 000 / 10 000, visible 200 / 250 / 300 | Популяция и bound соответствуют запросу; вне камеры остаются зарегистрированные движущиеся Entity; фактическая видимость записана |
| Пакеты 1 / 10 / 100 / 1 000 | requested, accepted, successful и задержки сопоставимы; следующая фаза ждёт завершения текущей |
| Stop при выпуске, удалении и Churn | Новых операций нет; принятые операции завершены; Activity закрывается без оставшихся Token, Entity и view |
| Частичная ошибка регистрации / размещения | Новые операции прекращаются; сохраняется failure; уже созданное очищается штатным закрытием Activity |
| Закрытие сцены при незавершённой работе | Runtime retirement ожидает журнал экономики; освобождаются leases, reservations, цели, препятствия, наблюдения и pool context |
| Поздние callbacks, повторный вход и три повтора | Старые Activity/handle/Life не управляют новой жизнью view; повтор имеет собственные Activity и pool context |
| Навигация | Записаны built/failed, waiting/blocked и native occupancy violations; ошибки алгоритмов не исправляются стендом |
| Normal / trace и счётчики | Отдельные папки и метаданные; недоступность обозначена явно; числа проверяются по иерархии профайлера без двойного учёта |
| Вложенные операции журнала | Handle/epoch различимы; измерение не складывает повторно вложенное продвижение того же record; проверить через существующие экономические сценарии |
| Переполнение | Прерванный неполный результат сохраняется, новые измерения не записываются за границей буфера |

Подготовленные тесты не считаются пройденными до разрешённого запуска. Производительность и отсутствие остаточных регистраций на полной популяции требуют захватов одинаковых конфигураций.

## Best Practices

Прогрев пула отделён от его расширения: повторная выдача и Instantiate имеют разную стоимость и не должны смешиваться в одном baseline. Lifecycle pooled view сохраняет Bind/Unbind и сброс предыдущих связей. [Unity: reusable code and pooling](https://docs.unity3d.com/6000.3/Documentation/Manual/performance-reusable-code.html).

ProfilerRecorder собирает завершённые кадры через LastValue и SumAllSamplesInFrame, освобождается вместе с запуском; данные заранее размещены в ограниченных буферах, экспорт выполняется вне измерения. Это сокращает влияние самого сбора на измеряемый участок. [ProfilerRecorder.LastValue](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Unity.Profiling.ProfilerRecorder.LastValue.html), [ProfilerRecorderOptions](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Unity.Profiling.ProfilerRecorderOptions.html).

Editor-замер не выдаётся за отдельную сборку. Wall time, inclusive counters и self time иерархии имеют разные границы; нормальный GC сохраняется, а стадии подготовки и очистки исключаются из среднего измерения. [Unity: main thread markers](https://docs.unity3d.com/6000.3/Documentation/Manual/profiler-markers.html).

## Поэтапная проверка нагрузки — working model

Начальный пресет: **1000 объектов, 250 видимых**. Автоматическая серия отклоняется до начала, если выбранные конфигурации содержат разные популяции. Пресеты 5000 и 10000 остаются доступными для отдельно согласованных ступеней.

Подготовка ограничена 180 секундами. Три последовательных полных Measuring-кадра дольше 1000 мс прекращают новую нагрузку. Эти ограничения переводят запуск в штатное завершение принятой работы и очистку; они не означают приемлемую производительность. Панель показывает готовую/запрошенную популяцию, очередь, стадию, её длительность и типизированную причину остановки.

`lifecycleSucceeded` и `statisticsSufficient` — независимые признаки. Для p95/p99 необходимо минимум 1000 полных Measuring-кадров; иначе значения -1 означают недоступность. Среднее, медиана и максимум малой выборки остаются описательными. Прерывание, ошибка и переполнение фиксируются отдельно. Полноценного baseline на 1000 нет: первый новый замер станет исходной точкой без заявления процента улучшения.

Первая матрица: **1000, один повтор**, Render; Lifecycle с пакетом 100 в Warm и Expansion; AI с бюджетами 64 и Population. Прогрев 30 с, измерение 180 с, одинаковые seed, камера и размещение. Normal и причинный trace сохраняются раздельно; Deep Profile выключен. Navigation/Churn и другие конфигурации не получают допуск из результатов этой матрицы.

После матрицы 1000 — **остановить прогоны, завершить очистку, представить промежуточный анализ и дождаться явного решения пользователя**. Только после принятия результатов можно провести согласованную матрицу 5000. После 5000 — такая же остановка и отдельное решение о 10000. Нет автоматического перехода по FPS, успешному завершению или старому разрешению на тесты. Неудовлетворительная ступень требует отдельного плана исправлений и повторной проверки на этой же популяции.

Отчёт каждой ступени включает времена кадров и шагов, фактическую нагрузку и частоту симуляции, подготовку/создание/удаление/очистку, очередь, аллокации, ошибки и ограничения данных. Непроверенные причины обозначаются `cause not established`.

Дополнительные файлы: `preparation-frames.jsonl`, `deletions.jsonl` и `activity-close.json` разделяют подготовку, отдельные удаления и закрытие Activity. Исходные CSV всех фаз сохраняются.

## Подготовка проверки текущего изменения

Новые EditMode-проверки: смешанная серия отклоняется до запуска; срок подготовки 180 с; сброс счётчика медленных кадров на границе фаз и после быстрого кадра; p95/p99 недоступны при 999 кадрах и доступны при 1000. Подготовлены профильные проверки общих Knowledge/economy контрактов, membership нескольких команд, immutable дельт и отдельных ревизий вложенных операций.

После завершения всей реализации и проверки компиляции **обоих проектов** требуется отдельное явное разрешение на тесты, Play Mode и первоначальные захваты. Подготовленные проверки до запуска не считаются пройденными.


## Компактные измерения Movement

working model: нормальный запуск сохраняет покадровые таблицы и сводки, без автоматических `.raw`/`.data`. Editor-адаптер отключает CPU recording и binary logging на время Normal. Существующий флаг trace выбирает TraceWindow: после прогрева записываются первые три полных CPU-кадра, затем начинается штатное завершение работы. CPUWindow выбирается типизированным PerformanceBenchCommandEvent с captureType=CPUWindow и trace=false. Это отдельные запуски; их доли времени нельзя переносить в продолжительный Normal.

minimum seam: настройки Profiler принадлежат PerformanceBenchProfilerAdapter; управление и завершение проходят через события. Экспорт окна начинается после cleanup. Пока он не завершён, следующий запуск серии не начинается. При ошибке, закрытии сцены и смене Play Mode настройки восстанавливаются, recorder и native view handles освобождаются.

Агрегированный экспорт v4 группирует только поток, статический маркер и родительский маркер. Идентификаторы Entity/process/operation не входят в ключи. Количественная metadata получает sum/min/max. Верхняя граница — 4096 групп; top 80 samples на кадр сохраняются с предками. Результат одного запуска, включая profiler bundle, ограничен 100 МиБ, детали — 8 МиБ. Усечение деталей и неполнота всего результата отмечаются раздельно. Версия 3 не мигрируется.

В bundle окна `categories.csv` и `frames.csv` показывают отдельные статьи Movement, Skills, AI, orchestration, GC, Editor, Profiler и прочих расходов. Время считается по self samples; знаменатель процентов — суммарное время главного потока только экспортированных кадров окна. `aggregates.csv` содержит подробную разбивку по статическим маркерам и родителям. Длительный Normal остаётся отдельным набором данных; его recorder durations не складываются с вложенными статьями окна. Manifest разделяет наблюдаемый рост памяти процесса при записи/загрузке native capture и дополнительные расходы экспортёра; точная память только native capture обозначена недоступной.

После реализации и компиляции требуется отдельное разрешение на тесты и Play Mode. ## Одно spatial-чтение и фазовая диагностика AI

**working model:** traffic делает один нефильтрованный spatial-запрос на позицию intent. Результаты сохраняются только в рабочем контексте прохода. Общий снимок строится по прежней occupancy matrix и регистрации профилей, после чего локальные результаты пересекаются с полным снимком. Повторные intents одной Entity остаются отдельными. `SpatialReadCounts` содержит Queries, VisitedCandidates и DistanceChecks; `NeighborCounts.DistanceChecks` равен нулю, потому что расстояния уже посчитаны. `ConflictRecords` считает конфликтные записи до дедупликации общего снимка. Движение, бюджет и выбор обходов не изменены.

**minimum seam:** `AI.Phase.*` размечает admission/контекст, узлы, forced target, чтение/построение/сравнение targets, transitions/pending enter, actions, skill owner/wait/target/activation, диагностический текст и completion/events. Run/Phase публикуются существующим workload context; Activity/Schedule/Step передаются фазами accepted tick с восстановлением корреляции при вложенных вызовах. `AI.Work.IdentityInclusive` считает фактические вызовы построения identity keys, сравнения и hash; вложенные показатели inclusive нельзя складывать. `AI.Work.Tick` считает вызовы HandleTick, Nodes — обработанные узлы, Actions — реально вызванные действия. Гипотезы об аллокациях ещё требуют разрешённого trace: **cause not established**. AI, Taxonomy и Skills не оптимизировались.

**minimum seam:** Editor-фасад `PrepareCurrentCaptureContext` вызывается синхронно при окончании прогрева перед CPU recording. `capture-preparation.json` и manifest сохраняют его длительность и настройки до записи. Пограничный кадр исключён; окно содержит следующие три полных кадра. Смена сборок, compilationStarted, script reload и retirement отменяют окно и восстанавливают настройки Profiler.

**working model:** v4 сохраняет native threadId. `ai-phases.csv` показывает вызовы, inclusive/self time и аллокации по фазам. `allocationBytes` — байты самих GC.Alloc samples; `directAllocationBytes` — непосредственные GC.Alloc children фазы; `subtreeAllocationBytes` — все её потомки (включает прямые, перекрывается с родительскими фазами). Missing-byte счётчики означают недоступные данные, а не нулевую аллокацию. Self-проценты имеют знаменателем суммарное время главного потока только кадров окна. Top 80 отдаёт приоритет главному потоку; worker waits остаются в агрегатах. Лимиты 4096 групп / 100 МиБ всего / 8 МиБ деталей и отсутствие автоматических native-файлов сохранены.

Подготовленные профильные проверки: TrafficPreparation_* и SpatialMeasuredRead_*; AIBrainDiagnostics_* и forced-target contract при обоих значениях detailed; ProfilerAggregateEditModeTests; ProfilerCapturePreparationEditModeTests; PerformanceBenchProfilerEditModeTests; существующие MovementService_Traffic* проверки результатов swarm/бюджета/yield/bypass. Их запуск требует нового явного разрешения после полной реализации и компиляции.

Ручной список после разрешения: разные spaces/Activity и отсутствующий requester; несколько intents, неподвижные соседи, удаление в callback и закрытие Activity; nested pass и освобождение сохранённых списков; правильные три полных кадра без PrepareCaptureContext; отмена/compilation/reload/scene close в записи и экспорте; вложенные аллокации и недоступные bytes/stacks; отсутствие .raw/.data и пределы размера. Падающие игровые наборы остаются отдельным ограничением, их восстановление сюда не входит. После AI1000 завершить очистку и остановиться для анализа. Допуск 5000/10000 по-прежнему требует отдельных подтверждений пользователя.
