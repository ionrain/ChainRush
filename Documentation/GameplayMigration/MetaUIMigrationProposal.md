1. EconomyAssetListSource загружает положительные holdings; сам по себе он не показывает отсутствующий закрытый контент. Для каталога нужны явно выданные записи, чья доступность описана состоянием; наличие записи в каталоге не даёт права использовать её в игре.
2. Юниты показываются одним EconomyListView без разделения на группы; выбранность отображается по runtime tag Selected. Ограничения количества в Action должны применяться к отдельной группе героев либо юнитов, а не ко всему смешанному каталогу.

5. GameFlowConditionEconomyMetric не имеет фильтра runtime tags. Проверка «этот герой есть в каталоге» не заменяет проверку «этот герой выбран и доступен».
6. EconomyAssetSelectionData сейчас не сохраняет EconomyEntryHandle из результата запроса, а EconomyListView сравнивает записи по asset. Перед операциями над персональными карточками, уровнем и развитием конкретизировать адресацию выбранной записи; совпадение asset само по себе не отличает записи разных кошельков/qualifiers.

## 3. Popup<T>: что именно перенести

**Переписать общую базу Popup<T> для существующего UIFlow.** Оставить передачу данных, Animator, позиционирование и визуальные события OnShow/OnShown/OnHide/OnHidden. Владельцем создания, закрытия и освобождения остаётся UIFlow.

Путь исполнения:

1. GameFlow либо медиированный UI-запрос открывает существующий UIPopupPresentationData.
2. UIFlow создаёт prefab и выдаёт UIHandle; типизированный контекст передаётся через IUIContextReceiver. Неподходящий контекст отклоняется, данные прошлого открытия не используются.
3. Popup применяет данные и запускает визуальное появление. Сам popup не загружает сцены и не меняет кошельки.
4. Кнопка закрытия отправляет запрос с UIHandle. При Hiding popup проигрывает закрытие; после окончания сообщает об освобождении через запрос к существующему Release.
5. Принудительное закрытие сцены освобождает обработчики и незавершённые визуальные действия. Позднее событие старого окна не воздействует на новое.

Добавить только отсутствующие request/response-контракты открытия, закрытия и подтверждения окончания анимации в существующую UIFlow-границу. Прямые вызовы UIFlowService из кнопок/анимационных компонентов не вводить. Не создавать PopupManager или вторую очередь окон. Контекст вопроса «да/нет» и ответы ConfirmationPopup в этом этапе не добавлять.

**Удалить из переносимой базы `modifyTimeScale` и запись в Time.timeScale.** Для минимальной меты остановка simulation при открытии окна не требуется. Боевые паузы остаются отдельной задачей lifecycle.

### 3.1. RewardPopup

**Working model, исправление согласовано пользователем:** перенести существующий RewardPopup в общий UI package, адаптировав данные и отображение к Framework. Сохранить его контракт: окно принимает готовые данные через Setup. Исходный RewardEvent.Transfer/End — один из способов открытия; LevelResultPopup передаёт данные в Setup напрямую. Общий путь открытия/закрытия — Popup<T>/UIFlow.

Конкретный объём:

1. Сохранить оформление окна, контейнеры карточек, иконки, форматирование количества, initialDelay/spawnCooldown, локальные эффекты появления и OnRewardsShown. Визуальные данные и ссылки задать в новых assets. Для отличающегося представления ресурса, персональных карточек и права на персонажа использовать явные настройки представления; не добавлять в Core игровые enum или проверки названий.
2. Передавать окну подготовленный список отображаемых позиций на данных Framework через общий контракт Popup<T> из §4.3 технического приложения. Количество принадлежит переданной позиции, а не текущему балансу кошелька. Иконки, подписи и форматирование брать из UI-данных assets и настроек представления. **Удалить из предложения RewardUIContext.** Идентичность получателя/записи Rewards и проверку Delivered убрать из обязательного контракта окна.
3. Разделить подготовку данных и показ. Источник с готовыми данными передаёт их в Popup<T>/UIFlow без чтения реестра. Для источника «награда выдана через Rewards» оставить RewardUIRequestAdapter: по явному запросу recipient + identity он читает RewardService, проверяет Delivered, подготавливает те же данные показа и открывает окно через UIFlow. Проверка доставки принадлежит этому обработчику; окно не вызывает RewardService. Асинхронный ответ привязать к request id и отмене, чтобы прежний запрос не открыл новое окно после отмены.
4. Открытие, последовательное появление карточек, OnRewardsShown и закрытие ничего не начисляют и не повторяют Claim/Grant. Доставка и защита от повторной выдачи остаются у Rewards/Economy. При закрытии или повторной настройке прекращать прежнюю последовательность показа и освобождать её карточки/обработчики; поздний callback прежнего открытия не меняет новое.
5. Старую подписку на RewardEvent и зависимости от IRewardList, RewardsData, RewardType и UnitData удалить из новой реализации. Сохранить локальные эффекты появления карточек. Перелёт иконок к счётчикам отложен пользователем как отдельная минорная задача; его компоненты, маршруты и пулы не включать в этот план и приёмку. RewardPopup показывает подготовленные данные без ожидания перелёта. Верхние счётчики отложены; балансы остаются в цене покупки.
6. Подготовить окно для показа переданных данных независимо от их источника. Новые источники наград этим пунктом не добавляются: финальная награда забега и LevelResultPopup остаются отдельной задачей второй фазы, daily/idle — вне этапа. Начальный seed Tabasco не превращать в автоматическое открытие наградного окна.

RewardListPopup и его RewardContainer не включать как скрытую зависимость: они обслуживают предварительный просмотр/получение награды в старом UI и остаются вне этапа.

Не подписывать окно безусловно на все события Rewards и не переоткрывать все Delivered-записи при входе в Main. RewardUIRequestAdapter обслуживает источник Rewards и не является обязательным посредником для прямого показа готовых данных. Владельцы, проверенные исходные вызовы и конкретные действия описаны в §4.4 технического приложения. До подключения источников наград второй фазы готовность окна означает готовность UI-компонента, а не завершённый игровой цикл получения награды.

## 4. Герои и юниты

### Authoring и UI

Исходные HeroUI/UnitUI сохранить для сверки. Для общего списка героя предусмотреть просмотр следующей/предыдущей записи; просматриваемая запись и выбранный для забега герой — разные состояния. Разделение существующего UnitSelector и перенос его связи с конкретными панелями отложить вместе с §4.2 технического приложения.

Для юнитов использовать один список всех записей каталога Unit, без разделения на группы. Selected отображать отметкой карточки. При обновлении сохранить просматриваемую запись по стабильной идентичности, не перестраивать все карточки на каждый кадр.

Настроить отдельные источники/кошельки каталога героев и юнитов. Action выбора героя: один выбранный, замена предыдущего. Action выбора юнитов: минимум один, максимум четыре, отказ при превышении. Ограничения и допустимость закрытой записи проверяются обработчиком операции, а не только Button.interactable.

Существующий EconomyListViewItemProfile сохраняет title/description/icon и tag events. Повторное событие выбора не добавлять: использовать onSelectionChanged списка. Общий источник числовых данных принимает текущую запись; поля задают selector ресурса либо Attribute, формат и получатель значения. Одинаковые запросы обслуживаются совместно; характеристики вычисляются одним общим проходом. Уровень и карточки читаются как ресурсы. EconomyItemProfileData с полями Level/Attributes/recipes не создавать. Цена и доступность покупки принадлежат ProductionUIAction/PurchaseButton. SpineEconomyItemProfile, SpineItemPresentationData, интеграционную сборку и mappings портретов/анимаций сейчас не добавлять.

**Spine и разделение панелей отложены пользователем.** Отдельно исследовать UnitPanel, UnitSelector и UnitMergePanel и согласовать, что относится к общим данным, навигации, представлению и интеграции Spine. Не фиксировать заранее их замену профилями ListView. Представление merge-форм, его анимации и подписи перенести в тот отдельный этап; исходные assets сохранить. Боевые merge-формы и применение к ним развития остаются в согласованном объёме. Подробности исключения — §4.2 технического приложения.

**Обновление UI:** при открытии панели сначала получать актуальные балансы и состояние, затем обновлять их по событиям Economy и подтверждённым результатам операций. Смена просматриваемого персонажа меняет подписки на его карточки/уровень; поздний ответ прежнего просмотра не перезаписывает новый. При закрытии панели снимать подписки. Не использовать только уведомления об изменениях без начального чтения и не опрашивать кошельки каждый кадр. Точный общий контракт источника/профиля включён в раздел 8.1.

### Состояние и разблокирование

- Запись каталога, право разблокировки, открытость, выбор, числовой уровень и карточки имеют разные значения. Не кодировать их одним балансом и не считать выделение карточки выбором в забег.
- Сохранить смысл исходных Locked → ReadyToBeUnlocked → Available; выбранность задаётся отдельным runtime tag. Нельзя выбрать или улучшить закрытую запись.
- «Разблокировать» подтверждает уже выданное право. Повтор не выдаёт персонажа или ресурсы повторно.
- В начальном seed отдельного профиля Framework выдать право на Tabasco: его начальное состояние — ReadyToBeUnlocked. Игрок сам нажимает «Разблокировать» в панели героя; автоматически открывать или выбирать Tabasco не нужно. Perfume, Water и Cola доступны по исходным настройкам. Ежедневные награды для этого шага не требуются.
- Сохранить исходный начальный выбор: Perfume — выбранный герой, Water и Cola — выбранные юниты. UnitData.Reset помечает defaultUnit как Selected; открытость этих трёх персонажей не означает пустой начальный состав.
- Данные состояния хранятся у игрока в Economy. Authored assets не меняются. Нового GameData, UnitStateData или CharacterManager не создавать.

Право, открытость и выбор должны проверяться обработчиком операции по актуальным данным. Простое назначение runtime tag кнопкой не реализует проверку права на разблокирование. Для выбора переиспользовать существующее изменение runtime tags: единственный источник выбранности — Selected на записи героя/юнита. Сборку или синхронизацию второго выбранного состава в Loadout не добавлять. Unlock использует Add Available с условием Entitled и отсутствием Available; проверку выполняет EconomyUIRequestAdapter по §4.1 технического приложения; новый универсальный исполнитель Unlock/Select/Upgrade не вводить.

### Прокачка через существующий Production

**Согласованное направление: working model.** Покупка — заказ существующему Production. Каталоги и рецепты задают цену и выпускаемые ресурсы развития; результат поступает в кошелёк конкретного героя/юнита. Предложение расширять EconomyCostDefinition и вводить отдельную составную операцию меты отклонено и удалено из объёма.

ProductionOrderRequest уже разделяет Payer и Recipient. ProductionInputData и ProductionOutputData уже используют LongProgressionData. UI передаёт выбранный рецепт и контекст выбранной записи через медиированную границу; цена и результат определяются Production. Резервирование, завершение и компенсацию переиспользовать из штатного lifecycle заказа. Покупку не выполнять цепочкой самостоятельных списаний из UI или GameFlow.

Получателя разрешать через точный handle записи и её постоянного runtime-владельца (§2 технического приложения). Production читает Level этого получателя в момент существующей ReservationPolicy, сохраняет аргумент для inputs/outputs и предоставляет ту же оценку UI (§3). Номер выпуска сохраняется отдельно; он не заменяет уровень персонажа. UI отправляет один запрос и наблюдает принятый OrderId; блокировка ввода задаётся authored Unity Events по §3.4. Общую дедупликацию Production и ExpectedProgressionArgument удалить из плана. OnEnqueue выставить в meta catalog данными; программного запрета сочетаний с другими ReservationPolicy не добавлять. Мета не создаёт Release.

Один жест UI создаёт один заказ. До отправки выставить ожидание и вызвать authored OnPurchaseStarted; в Main настроить блокировку ввода через Unity Events. OnPurchaseEnded вызывается после результата; отказ до принятия, ошибка и отмена тоже завершают ожидание. Постановка заказа в очередь не является успехом. Перед следующим нажатием обновить цену и balances. Принятую команду не отправлять повторно, её состояние читать по OrderId. Ради этого не менять admission, очередь или ReservationPolicy Production и не добавлять реестр заблокированных получателей. Существующие отказ/компенсация остаются у Production/Economy.

**Универсальность кнопки — working model:** перенести BuyButton под именем PurchaseButton как представление цены и доступности, без Level, Hero/Unit и Upgrade. В исходнике кнопка получает Setup/UpdatePrice/UpdateBalance; конкретные UnitPanel.Upgrade и EnergyPopup.BuyEnergy назначены через Button.onClick в Main. В новом пути отдельное общее ProductionUIAction отправляет заданные данные покупки посреднику и связывает результат с событиями кнопки. OnActive/OnInactive сохранить отдельно от OnPurchaseStarted/OnPurchaseEnded. Энергию это сравнение не включает в перенос.

Исходные цены и характеристики перенести явными authoring-данными. LongListProgressionData позволяет сохранить таблицу значений на диапазоне уровней без нового игрового вычислителя степенной формулы. По решению пользователя стоимость вычисляется по текущему уровню до повышения: первое улучшение стоит 1000 монет. Это же значение показывается в UI и списывается при подтверждении операции. Карточки также рассчитываются до повышения уровня.

Сохранить предел 100 отображаемых уровней: внутренний 99 не имеет следующей покупки. На пределе UI показывает максимальный уровень, а обработчик отклоняет повышение без списания и без обращения к элементу прогрессии за её пределами.

**Начальные ресурсы согласованы:** при создании отдельного профиля Framework выдать 4000 монет и по 5 персональных карточек Perfume, Tabasco, Water и Cola. Этого хватает на первое улучшение каждого; Tabasco перед улучшением нужно разблокировать. Это явное изменение исходной базы 1000 монет / 0 карточек, а не новый источник регулярных наград. При повторном входе восстанавливать остатки из сохранения, не выдавать этот запас повторно. Подробности — раздел 8.2.

### Связь с перенесённым боем

Переиспользовать существующую проекцию Attributes и CapabilityHostAttributeSourceData для чтения развития из постоянных кошельков персонажей. Сейчас боевые assets читают DevelopmentWallet участника; подключить кошелёк конкретного персонажа через существующий CapabilityHostAttributeSourceData и описанный entryPath владельца (§2.3 технического приложения), без второй копии его развития. Удалить фиксированный seed развития из игровых стартовых вариантов после подключения постоянных данных. Существующее монтирование кошельков не должно повторно выдавать стартовые значения при каждом забеге.

Уровень развития не заменять номером merge-формы. Повышение уровня обычного юнита обновляет необходимые значения для всех его уже используемых форм по исходным данным. Итоговые Power/Defense/Health/Speed/SkillSpeed должен читать тот же существующий боевой путь; отдельную формулу для цифр на панели не создавать.

При переносе таблиц учитывать уже согласованные AttributeData.Precision и единый положительный Rate для SkillSpeed из D4/D9 [ReworkConnections.md](ReworkConnections.md). Общее указание «перенести исходные числа» не разрешает вернуть Duration или старую семантику уменьшения задержки. Зафиксировать таблицу исходных и целевых raw-значений, qualifiers и merge-множителей; UI форматирует те же значения согласно Precision. Кошелёк постоянного развития не должен сохранять временные баффы забега.

## 5. Выбор и запуск уровня

Сохранить фон Location001, её оформление и два действующих маркера уровней. LocationBlank и уровни 3–5 не делать доступными кнопками. Состояния закрыт/доступен/пройден и выбранный уровень хранить в постоянной Economy-модели игрока.

Оба уровня доступны в начальном профиле по исходным required = null. Сам запуск не помечает уровень пройденным и не открывает следующие уровни. Запись подтверждённого прохождения остаётся у завершения забега второй фазы; UI отображает состояние, но не присваивает результат.

Переписать визуальную часть BattlePanel в общий профиль выбора контента на основе ListView: фон/подпись, маркеры, выбор. Убрать из неё списание ресурсов, изменение LevelData и самостоятельный запуск сцены.

Кнопка запуска отправляет существующее событие GameFlow. В условиях проверить доступность уровня и корректный состав. Для связи выбранных runtime tags с условиями доработать существующий GameFlowConditionEconomyMetric и его чтение/наблюдение; не создавать ChainRushStartManager. Оставить две конфигурации уровня — Survive и Distance. GameFlow выбирает уровень; определение выбранного героя не создаёт отдельную ветку запуска. Героя независимо выбирают в мете через Selected. Seed Activity создаёт фиксированного служебного host с Production; стартовое Objective запускает выбор и выпуск одного героя из кошелька участника через Population/Orchestration и существующую материализацию Activity.

**Согласовано пользователем:** выбранность героев и юнитов хранить runtime tag Selected. Материализовать героя, удовлетворяющего Hero + Selected; юнитов допускать по Unit + Selected. Board читает доступные навыки из кошелька выбранного героя. Связи и критерии задавать assets. Удалить фиксированный стартовый состав из переносимых конфигураций после подключения этого чтения. Второй изменяемый Loadout, его синхронизацию и сборку снимка перед запуском не добавлять.

**Исправление технического предложения:** удалить из плана сохранение четырёх комбинаций «уровень × герой». После переноса ссылок удалить отдельные Tabasco Activity/flow нового пути. ActivityWalletSeedEntryData оставить с конкретным asset служебного host. Удалить предложенные source type Authored / ParticipantEntry, новый enum и разрешение выбранного героя внутри SeedWallets. Согласованный путь выпуска выбранного героя описан в §§2.4–2.5 [MetaUITechnicalPlan.md](MetaUITechnicalPlan.md). В §2.6 зафиксирован владелец цели уровня — Activity с её Objectives/Analytics/Orchestration. Пользователь отдельно согласовал одинаковые боевые свойства героя в обоих режимах. В §2.6 перечислены удаление Distance-дублей и перенос поставщиков зон в общие префабы.

**Что требуется подключить:** существующий EconomySelectionQuery поддерживает asset/runtime-tag фильтры, но PopulationContentRuleData их сейчас не передаёт и читает только один кошелёк участника. Уже существующий EconomyRuntimeWalletGraph/проекция умеет обходить вложенные кошельки у CapabilityHost; это не означает, что такой обход уже подключён к Board. Использовать описанные в техническом приложении entryPath владельца, выбор содержимого Population и обычный seed служебного production host; новый кошелёк вариантов героя по цели уровня не добавлять. Не объявлять весь переход выполненным одним изменением фильтра и не добавлять новый resolver, пока не проверены существующие владельцы. Подробности — §§2.1–2.6 технического приложения.

**Согласованный working model начального появления:** один общий host, каталог с рецептами Perfume/Tabasco; каждый рецепт требует Available + Selected через Require постоянной Stack-записи и выпускает один Token. Стартовое Objective требует одного Hero; Population с объёмом 1 выбирает содержимое через общий selector §2.4. Постоянная запись и развитие не расходуются. Production выполняет выпуск, Activity подтверждает появление. После успеха Objective не повторяется по смерти героя. Отдельного игрового C#-материализатора и вариантов уровня на каждого героя не добавлять.

Повторное нажатие Start во время принятого запуска не создаёт второй забег. Временную блокировку кнопки даёт состояние GameFlow; окончательное принятие принадлежит штатному пути запуска Activity.

Состояния запроса запуска — принятие, подготовка Activity, Ready и ошибка с возвратом управления в Main — подключить согласно §4.5 технического приложения. По последнему решению пользователя переход завершается по ActivityReady; ожидание героя и обработку Failed процесса Orchestration вынести в отдельный шаг. Семантику ActivityReady не менять. Новая мета входит в новый Board + Autobattle, а не загружает старую Level с менеджерами. GameFlow/UIFlow владеют переходом и Loading; отдельный GameSceneLoader, независимо вызывающий SceneManager для того же перехода, не подключать. Основной запуск в Build Settings и окончательный возврат после победы/поражения остаются отдельными пунктами второй фазы. Не считать их реализованными наличием кнопки Start.

В этом этапе запуск бесплатный: убрать из нового пути проверку и списание 5 энергии, переход в магазин при нехватке и элементы UI, предлагающие её восстановить или купить. Энергию, её восстановление и покупку перенести отдельным шагом; остальные проверки доступности уровня и состава сохранить.

## 6. Сохранение и исключённые механики

Использовать существующие PlayerData/WalletEntry/SeedEntry и EconomyStorageBridge. Сохранение должно охватывать открытых персонажей, выбор героя/юнитов/уровня, уровни развития, персональные карточки и валюту. При повторном открытии Main читать сохранённое состояние, не восстанавливать его из настроек UI.

**Согласовано:** отдельный профиль Framework с явным исходным seed. Старое сохранение не читать как состояние новой меты, не преобразовывать, не перезаписывать и не удалять. Разделение должно действовать и при обычном сохранении/завершении приложения, а не только при первом старте. Автоматическую миграцию GameData не добавлять.

Проверено: EconomyStorageBridge использует ключ economy.state/current и SettingsContext по StableSimulationKey каждого владельца; стандартный Storage пишет в persistentDataPath/morboo/settings. GameManager старого пути использует MMSaveLoad и свой файл/каталог. В новых сценах старый GameManager не должен запускать Load/Save. До authoring зафиксировать стабильный идентификатор нового профиля и порядок «начальный seed при отсутствии профиля / восстановление существующего». Не сбрасывать кошельки при повторном открытии Main.

**Согласованная адресация:** сохранить ключи EconomyStorageBridge без изменения. PlayerSnapshot.StorageContext не подставлять в сохранение Economy; новый PlayerData.Id отделяет профиль Framework.

**Согласованный момент сохранения:** после каждого подтверждённого изменения меты, на паузе приложения и при штатном завершении. Подключение Economy tag-action, ProductionOrderYielded/Finished, dirty revision и результата записи описано в §5 технического приложения. Shutdown-путь при покупке не вызывается. Показ ошибки сохранения и ручной повтор отложены пользователем; остаются автоматическая запись, сообщение результата и диагностика. По решению R3 случай незавершённой покупки отложен: не вводить автоматическую отмену, сериализацию заказов, блокировку записи или переработку возврата. Гарантия восстановления прерванной покупки не является критерием текущего этапа.

Не переносить сейчас: энергию, её восстановление и покупку, магазин, IAP/ads, daily/idle, экипировку, покупку отдельных навыков, tutorial и tutorial-блокировки вкладок, рейтинги, социальные окна, новые персонажи, новые уровни. Нужные вкладки меты должны быть доступны без старого TutorialManager. Полный результат забега/HUD и внешние награды остаются другими пунктами второй фазы. Разблокировка Tabasco в этом шаге не зависит от них: право задаётся начальным seed.

Из окон отдельно отложить ConfirmationPopup и RewardListPopup. **RewardPopup входит в текущий перенос** как существующее окно показа готовых данных; перенос полного экрана результата забега этим не подразумевается.

## 9. Best Practices

**Разделение данных контента и исполнения.** Unity показывает этот подход на ScriptableObject-based game setup: параметры и ссылки оформляются данными, поведение переиспользуется. Здесь это четыре определения персонажей, две конфигурации уровня и UI-профили; пользовательское развитие остаётся в runtime/Storage, не записывается в authored assets. [Unity: Separate game data and logic](https://unity.com/how-to/separate-game-data-logic-scriptable-objects).

**Разделение чтения и команд.** CQRS применяется к интерфейсам, которые показывают состояние и отправляют действия. Здесь достаточно одной Economy-модели: UI получает данные/оценку операции, а владелец команды повторно проверяет и изменяет состояние. Отдельная база, event sourcing и новая очередь меты не требуются. Это устраняет зависимость корректности покупки от состояния конкретной кнопки. [Microsoft: CQRS](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs).

**Единственный владелец lifecycle.** Уже существующий UIFlowServiceCore создаёт popup, передаёт контекст и ожидает manual release. Popup<T> должен исполнять визуальную часть этих переходов, а не повторять хранение/создание/удаление окна. Источники: `/Users/ionrain/MorbooFrameworkPackage/Scripts/Core/UI/Flow/UIFlowContracts.cs`, `UIFlowServiceCore.PreparePopup/ClosePopup/Release`, существующие исходники `UIFlowServiceEditModeTests` (не запускались).
