## Existing System Fit

- **EconomyServiceCore и Economy modules** владеют чтением и авторитетными балансами. Сначала нужно устранять стоимость общего чтения: оно одновременно обслуживает Knowledge, projection, runtime wallet graph и копирование кошельков при материализации. Отдельный вычислитель балансов для каждого потребителя не нужен.
- **KnowledgeResourceSourceHandler / KnowledgeSourceHandlerContext** владеют обновлением resource read model. Изменённый Wallet уже используется; сохраняются поддержка форм, привязок Entity и замена существующих record sets.
- **EconomyRuntimeWalletBinder / EconomyRuntimeWalletGraph** владеют локальными кошельками и графом вложенных владельцев. **CapabilityHostSkillController / SkillHostProjectionCore** владеют наблюдением, projection и согласованием live state. Тяжёлые пересборки подтверждены; какие из них можно убрать без потери наблюдения, требует отдельного разбора входных изменений.
- **DeferredRuntimeWorkQueue** объединяет работу по ключам и завершает её после событий. В игровых кадрах максимальный возраст работы — 0 кадров, max pending после раунда — 4. Накопление очереди не подтверждено; дорого исполняются её callbacks. Менять общую очередь по этим данным оснований нет.
- **Spatial / WorldTargetResolution** владеют поиском и 3D-геометрией; **AIBrain** — пригодностью цели и выбором поведения. Цели остаются Entity. Детальный план оптимизации фильтрации кандидатов пока не составлен.

## Best Practices и границы вывода

Сначала сокращать работу общего производителя дорогих данных, затем проверять необходимость повторных пересборок потребителей. В проекте уже есть фильтрация GetSelectionAssets для точного запроса, частичное обновление Knowledge по ключу owner + wallet и TryDeferUnique для объединения работы host. Их существующие владельцы сохраняются; отдельный кеш-сервис, новый планировщик и изменение частоты simulation не предлагаются.

При чтении вложенного профиля нужно отделять собственное время от дочерних samples. Кадры 1045 и 1284 непосредственно показывают, почему большой marker не всегда означает дорогой алгоритм этого владельца: внутри записана GC.Collect. При этом аллокации QueryWallet / projection и стоимость materialization подтверждены отдельно. Render Thread в тяжёлых кадрах ожидает Main Thread; GPU не объясняет выбранные пики. Накладные расходы Editor/Profiler присутствуют, поэтому результаты нельзя выдавать за замер сборки.

Приоритет следующей работы: общий путь чтения кошельков и его временные структуры → пересборки графа/проекции Skills при изменении кошельков → стоимость поиска целей. Конкретные изменения runtime сверх ранее согласованной оптимизации в этом исследовании не реализованы. Полный план таких изменений и их lifecycle-инвалидации ещё не согласован. Утечка удерживаемой памяти этим захватом не доказана; подтверждены высокие временные выделения и длинные сборки мусора.

## Исправления Economy/Knowledge по запросу пользователя

**Working model.** Основание: «Хорошо, внеси исправления по Economy/Knowledge». Изменены два существующих runtime-файла package; authoring и публичные контракты не расширяются.

- **EconomyServiceCore.cs / QueryAllBalances:** читать значения через существующий IEconomyModule.TryGetMetric, сохранив общий выбор модуля и проверки через выделенный private TryResolveQueryMetric. Этот же метод использует BuildRoutedQuery. Для внутреннего словаря балансов больше не создавать массив EconomyMetricKey, группы маршрутизации, сортируемые списки и массив EconomyMetricSnapshot. Адрес разрешается один раз. В словарь включать ненулевые значения, включая отрицательные; отсутствие ключа читатели уже трактуют как ноль. Зарегистрированные определения по-прежнему обходятся — нового индекса содержимого кошелька нет.
- **EconomyServiceCore.cs / BuildWalletQueryItems:** выделять коллекции по фактически добавленным записям, а словарь агрегации — только для агрегированного запроса. В запросе Stack считать все токены для вычитания из общего баланса, но не строить их представление. В запросе Token не строить представление Stack. Не создавать runtime-теги пустого Stack, который не попадёт в результат. Сохранить detailed/aggregated, IncludeZeroBalance, committed/available, фильтры, сортировку результата и расчёт полной вместимости кошелька.
- **KnowledgeResourceSourceHandler.cs:** в обработке одного EconomyEntryChangeEvent или EconomyTagChangeEvent лениво читать изменённый кошелёк один раз для Stack и один раз для Token. Использовать эти items во всех наблюдающих его командах и доменах. Фильтры Knowledge, Entity/позиция, записи, индексы ExternalKey и уведомления остаются отдельными для каждого state. Массивы живут только в локальных переменных вызова; между событиями ничего не кешируется. Первичное наполнение и обновление привязок Entity используют тот же построитель записей.

**Existing System Fit:** EconomyServiceCore остаётся владельцем разрешения адресов, представления Stack/Token, проверки вместимости и существующего event-scoped query cache. Проверены все 12 реализаций IEconomyModule.TryGetMetric: они читают баланс соответствующего домена. QueryAllBalances также используется точным QuerySelection и проверкой вместимости перед операцией; эти читатели сохранены. KnowledgeResourceSourceHandler владеет resource slices; KnowledgeSourceHandlerContext заменяет record sets и индексы. KnowledgeBroker синхронно инвалидирует Analytics и откладывает публичные уведомления до окончания EventBus dispatch. Единственный подписчик KnowledgeBroker.Invalidated — ActivityAnalyticsService.MarkKnowledgeDirty; он помечает чтения устаревшими и не меняет Economy. Поэтому между перспективами этого обработчика нет операции, требующей повторного чтения кошелька. CloseDomain/Reset, смена ExternalKey, modifiers invalidation и очередь уведомлений не изменены. Пересборки Skills, частота Analytics, поиск целей и Production lifecycle вне текущей правки.

**Best Practices:** оптимизация применяется у владельца данных и убирает промежуточное представление, не создавая второго источника балансов. Точный используемый контракт — Economy/IEconomyModule.cs: TryGetMetric; тот же вызов уже использовался в EconomyServiceCore.Query. Повторное чтение объединяется в пределах одного синхронного события: локальное время жизни данных не требует инвалидации между событиями и очистки при закрытии домена. Граница подтверждена Events/EventBus.cs: Trigger → EnterPhase/ExitPhase(AfterEventDispatch), Knowledge/KnowledgeBroker.cs: NotifyChanged/QueueFlush и Activities/Analytics/ActivityAnalyticsService.cs: MarkKnowledgeDirty. Существующий длительный кеш не расширяется.

**Проверка без исполнения:** просмотрены все читатели QueryAllBalances и ветки формирования Stack/Token, существующие сценарии разделения форм, committed/available токенов и стабильной идентичности owner/wallet. Выполнены чтение diff и git diff --check; ранее staged изменения сохранены. Тесты, сборка, Play Mode и новый Profiler не запускались. Удаление перечисленных выделений следует из кода; снижение миллисекунд и байт после правки ещё не измерено. Предыдущий профиль остаётся свидетельством до изменения, а не результатом проверки после него.
