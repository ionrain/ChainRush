## Best Practices

- **Один владелец принятия и завершения операции.** `ProductionRuntime.TryEnqueueOrder`, `TryConfirmOutput` и `CommitYield` уже разделяют admission, появление и commit. Cooldown подключается к появлению, учёт окончательного выпуска — к commit. Объединение этих моментов исказило бы компенсацию. Источник: [ProductionRuntime](/Users/ionrain/MorbooFrameworkPackage/Scripts/Core/Production/Internal/ProductionRuntime.cs).
- **Наблюдение не создаёт наблюдаемую операцию.** Существующий `ObjectiveConditionExternalFactState` читает факт; этим можно заменить производственное владение внутри Objective. Но его текущий глобальный строковый registry нельзя использовать для разных попыток без изменения scope. Точное изменение описано в D11. Источники: `ObjectiveExternalFactStatePlugin`, `ObjectiveExternalFactStateRegistry`, `ObjectiveOrchestrationFactContainer` в package.
- **Один источник характеристики и одна проекция.** `CapabilityHostSkillController` уже подписывается на кошельки и обновляет проекцию; `SkillHostProjectionCore` применяет derived rules. Для усилений расширяется список входных источников, а не добавляется второй расчёт Power/Health/Speed. Источники: `CapabilityHostSkillController.ReplaceWalletWatches и создание EconomyProjectionRequest`, `DerivedAttributeRuleData`, `DerivedAttributeTermData`.
- **Локальная память поведения.** `TryGetActionRuntimeState/SetActionRuntimeState` уже отделяют данные исполнения действия от общего TargetControl. `TimeInStateAIBrainConditionData` считает время текущего узла, поэтому память всей погони требует отдельного стабильного узла, а не таймера в записи цели. Источники: `AIBrainContracts`, `TimeInStateAIBrainConditionData.Evaluate`.

Это применение проверенных механизмов самого проекта. Наличие механизма не означает, что все перечисленные ниже authoring-подключения уже реализованы.

## D2. Analytics → Objective → Orchestration → Economy

**Working model; выполнено по шагам 3–4 [промежуточного плана](PrePhase2Corrections.md).** Удалены ActivityNumericEconomyFeatureData, оба её источника, ActivityNumericSourceData и три progress-feature assets.

ElapsedSimulationActivityAnalyticsMetricData измеряет simulation-время настроенной Activity. EntityMovementActivityAnalyticsMetricData наблюдает позицию одной Entity через Knowledge; политика выбирает смещение вдоль оси либо сумму последовательных перемещений. ChainRush использует неотрицательное смещение вдоль X; движение 10 вперёд и 10 назад даёт 0. Метрика пути учитывает телепортацию как изменение позиции. Идентичность и origin не меняются при повторном reader; потеря источника означает Pending, неоднозначный выбор — Error.

ObjectiveLongTargetProgressionData выбирает Resource либо Analytics. ObjectiveNumericTargets владеет чтением, подпиской и runtime-порогом; Pending не подменяется нулём. До готовности дочернего порога составной факт целиком не передаётся в Orchestration, чтобы не менять смысл AND/OR. Готовый факт — прежний EconomyAmount.

SurviveProgressObjective задаёт баланс времени/300; PerfumeDistanceProgressObjective и TabascoDistanceProgressObjective — смещения/150. LongProgression ограничивает результат шкалой 0…1000000 и использует существующее округление. PlayerBrain содержит обычные Issue/Consume operators для LevelProgress. Economy endpoint перечитывает баланс; отдельного писателя/накопленной дельты нет.

Частота публикации — reviewInterval Analytics, порядок AfterProduction и бюджеты сохранены. Запись прогресса может отставать от simulation. Population и вражеские Objectives продолжают читать общий кошелёк. Полное завершение забега остаётся во второй части.

## D3. Выбор доски → эффект → следующий ход

**Актуальное решение Heal:** [HealResourceFormulaPlan.md](HealResourceFormulaPlan.md). Общие ресурсные формулы, registration, снимок действия, один Heal и выдача N через навык Board внесены в код и assets. Реализация D3 завершена; приёмка игрового поведения не проводилась.

**Implementation decision: working model. Решение пользователя:** Board выпускает Stack навыка; у игрока заранее задан исполнитель; Orchestration назначает ему выполнение; мозг исполнителя выбирает Entity-цели; использование навыка потребляет ресурс этого навыка из стека. Юниты являются целями Heal и баффов, а не исполнителями самолечения.

1. **Переписать результат выбора Board:** для Heal один IssueHeal исполняется BoardHost через SkillDecompOpData. Два числовых Economy effects одним commit расходуют N выбранных HealBoardBase Tokens и выдают N Stack Heal в общий кошелёк участника. Количество определяется общей ресурсной формулой, отдельные варианты по длине цепочки удалены. Unit merge/deployment сохраняет Production. Остальные согласованные эффекты перенести по их пунктам D3–D4.
2. **Задать исполнителя в стартовых данных игрока для Autobattle.** Использовать существующие CapabilityHost, wallet seed, AIBrain и Skills. Исполнитель существует до получения ресурса навыка. Production не создаёт исполнителя при каждом выборе карточек. Не добавлять игровой класс исполнителя или отдельный менеджер эффектов.
3. **Подключить назначение через существующую Orchestration Autobattle.** Её Objectives наблюдают Stack в кошельке игрока. Каждому навыку соответствует authored состояние мозга с уже настроенным UseSkillAIBrainActionData; Orchestration назначает исполнителю это состояние. SkillData в AIBrainControlOrder не добавлять. Board не передаёт исполнителю SelectionRequestId, handles клеток, список целей или адрес другой Activity. Мозг выбирает Entity-цели после назначения.
4. **Оставить выбор целей мозгу исполнителя.** Его authored query выбирает подходящие Entity. Heal воздействует на юнитов как на Target; исходные параметры лечения берутся из skill assets. Для HeroSkill исполнителем остаётся герой. Orchestration не превращает получателей Heal в отдельных исполнителей.
5. **Потреблять Stack при использовании навыка через Skills/Economy.** Решение пользователя: оставить списание экономическим эффектом навыка; отдельное экономическое действие мозга не добавлять. Для LightningBolt списывать одну единицу Stack соответствующего уровня за применение, включая применение без найденных целей. Heal расходует накопленное N по HealResourceFormulaPlan; Buff расходует накопленные процентные пункты по D4. Отсутствие целей не должно останавливать выполнение до списания: эффекты, которым нужны эти цели, не выполняются; применение заканчивается без ожидания новых целей и без повторного расхода. Количество списаний не зависит от числа целей и повторений боевого действия внутри одного применения. Ошибка экономической операции остаётся ошибкой; эффект не считается оплаченным без её commit. Не вводить Token-запрос, отдельный захват Token, таблицу межактивностных запросов или протокол ответов поверх кошелька.
6. **Применять постоянный Buff через источник D4:** навык исполнителя выдаёт усиление в кошелёк игрока; существующая проекция применяет его к подходящим текущим и будущим юнитам. Не возвращать игровое копирование итоговых атрибутов в каждого юнита.

**Исполнение без цели — решение пользователя, working model:** добавить на SkillData галку `ExecuteWithoutTarget`, по умолчанию выключенную. При включении навык с типом цели Entities принимает пустой список Entity. Для непустого списка сохраняются прежние проверки количества, существования и tags; Self сохраняет прежний контракт. До расчёта формул и применения effects пропускать эффекты, которым нужна отсутствующая цель, без ошибки, событий применения и записи в AppliedEffects. Остальные effects, включая списание из кошелька игрока, проходят обычное исполнение. Зависимость от цели определяет сам тип effect: получатель Target, чтение Target в формуле, движение к цели, создание направленного на цель carrier, источник/получатель Target у переноса Economy entries. Одно правило использовать в оценке результата и runtime-исполнении. Не подставлять Owner вместо отсутствующей цели и не превращать невалидную переданную Entity в пустой список. Настройка не отменяет явно заданные requirements, reload или занятость execution slot; для применения без цели не задавать обязательное наличие пути/дистанции как общее условие запуска.

**Кратность effect — решение пользователя, working model:** enum `SkillEffectRepeatType` на SkillEffectData: `EveryAction = 0` по умолчанию и `OncePerExecution = 1`. Для списания Stack задать OncePerExecution; боевые повторы оставить EveryAction. Runtime отмечает effect в существующем AppliedEffects только после успешного commit; повторные действия этого исполнения пропускают уже применённый OncePerExecution. Длительный effect продолжает свой обычный lifecycle без повторного запуска. Пропущенный из-за отсутствия целей effect не считается выполненным. Новое применение получает новую запись исполнения. Оценка выдаёт суммарные дельты и число выпускаемых carriers с учётом кратности; переполнение делает оценку неуспешной. Отдельный реестр списаний не добавлять.

**Уточнение пользователя о границе Skills/AIBrain:** навык не обязан иметь мозг. Назначение authored состояния относится к исполнителю D3 и не является общим контрактом выполнения Skills. Предложенную настройку SkillDecompOpData «ждать выхода из состояния мозга» пользователь не согласовал; её не добавлять. Текущий SkillDecompOpData создаёт только AIBrain endpoint, а добавленный CollectExecutionStates ещё и исключает исполнителей без подходящего состояния мозга. Эту общую зависимость нельзя считать принятой working model. Сам Skills runtime исполняет SkillExecutionRequest и предоставляет SkillExecutionRef/SkillExecutionObservation без зависимости от AIBrain. Перед продолжением изменения общего пути декомпозиции требуется конкретно определить подключение к этому lifecycle.

**Граница Activity:** связь Board и Autobattle проходит только через кошельки. Каждая Activity исполняет собственную Orchestration и управляет собственными hosts. Прямые межактивностные запросы, сообщения, callback и ссылки на чужую Orchestration запрещены.

**Удалить из решения:** непосредственное назначение Skills из SelectionResultEvent; Token конкретного применения и связь SelectionRequestId → Token → ответ; производство временной Entity-исполнителя; обязательный новый SupportHost как специальный механизм; самолечение выбранными юнитами; расширение ObjectiveSkillResult ради межактивностного ответа. Удалить три игровых слушателя Selection и их dedup-словари после подключения штатного пути.

**Порядок Board — решение пользователя:** после подтверждённого Production/Economy commit выдачи Stack оплатить BoardTurnToken, очистить остатки и заполнить доску. Autobattle использует выданный ресурс самостоятельно; Board не ждёт применения навыка. Удалить прежнее требование ожидать окончания боевого навыка и весь предложенный для него протокол ответа.

**Атомарные операторы — согласованное решение, working model:**
- **Переписать SkillDecompOpData:** сохранить оценку результата Skills и требования, удалить поиск состояний мозга и создание AIBrain endpoint. Выдавать прямое назначение одному исполнителю Skills. SkillOrchestrationEndpointRuntime запускает SkillService, хранит конкретный SkillExecutionRef и завершается по результату этого исполнения. Достижение наблюдаемого факта не отменяет принятое исполнение. Явная отмена отменяет только его SkillExecutionRef; терминальное событие приходит после освобождения ресурсов исполнения.
- **Добавить AIBrainDecompOpData:** authored соответствие факта, селектора исполнителя, node и state. Не искать UseSkill внутри графов и не добавлять SkillData в AIBrainControlOrder. Для D3 этот оператор назначает заранее настроенное состояние поиска целей и использования навыка.
- **Переписать AIBrainOrchestrationEndpointRuntime:** ждать результата назначенного состояния. Достижение факта не отменяет приказ. Отмена, Reset и закрытие Activity прерывают приказ; синхронное завершение во время приёма учитывается. Это lifecycle оператора AIBrain, а не настройка завершения SkillDecompOpData.

**Список целей — решение пользователя, working model:** AIBrain хранит выбранный список Entity; SelectEntityTargetByQueryAIBrainActionData и SelectActivityTargetAIBrainActionData получают явный режим выбора всех подходящих целей. Пространственный запрос сохраняет радиус; запрос Activity выбирает hosts только своей Activity. Heal использует запрос Activity. UseSkill и проверка готовности передают весь список в одно исполнение Skills. Событие изменения целей, snapshot, учёт назначений и очистка работают со списком. Потребители одиночной цели принимают только список из одной Entity, без молчаливого выбора первого элемента. TargetEntityExists проверяет наличие хотя бы одной существующей Entity. Цели принятого приказа очищаются при его освобождении.

**Existing System Fit:** Selection и Production Board владеют обработкой клеток и выпуском Stack; Economy — кошельком, остатком и списанием; Objective/Orchestration Autobattle — наблюдением потребности и назначением исполнителя; AIBrain — состоянием поведения и выбором Entity-целей; Skills — конкретным исполнением и эффектами; Activity — seed, регистрацией и cleanup исполнителя. Выбор hosts всей Activity уже реализован в SelectActivityTargetAIBrainActionData; пространственный выбор принадлежит SelectEntityTargetByQueryAIBrainActionData/WorldTargetResolution. Оба используют AIBrainTargetEligibilityUtility. Проекция D4 применяет постоянные усиления. Межактивностный диспетчер не добавлять.

**Best Practices:** использовать существующий обмен через Economy: BoardMergeRecipe1 выдаёт Stack, другая Activity самостоятельно выбирает способ использования. Разделение атомарных операторов сохраняет владельцев исполнения: Skills завершает SkillExecutionRef, AIBrain — свой приказ. Повторять уже имеющийся lifecycle через ожидание чужого домена не требуется. Конкретные опорные контракты: SkillService.TryExecuteAsync, SkillExecutionTerminatedEvent, AIBrainControlChangedEvent и IOrchestrationEndpointRuntime.TryComplete.

**Статус реализации:** разделение операторов, отмена конкретного SkillExecutionRef, завершение собственного исполнения endpoint и передача списка целей добавлены в код. ### D6: общая граница simulation step — согласовано и внесено

**Verified до правки (чтение кода, не воспроизводящий запуск):** `RealtimeScheduleRuntime.Update` может вызвать несколько `SubscriptionTickSource.Dispatch` до возврата в `GameRuntimeHost.PumpRuntime`. Второй носитель runtime tags — сам `SkillCarrierRuntimeRecord`; его значения принадлежат Skills. `AfterScheduleDispatch` в существующем DeferredRuntimeWorkQueue закрывается после всего Update/Advance, а не каждого отдельного шага. Её используют GameFlow, Drops, Production materialization и Knowledge; переопределять её смысл ради Skills нельзя. Готового уведомления после каждого Dispatch в Scheduling нет.

**Inference:** если оставить только локальную очередь Skills до конца кадра, защита, выданная при обработке раннего шага этой очереди, не получит уже прошедшие callback следующих шагов CapabilityHost. Поэтому такая реализация не обеспечивает одинаковое поведение при одном и нескольких шагах за кадр. Причина runtime-ошибки не установлена воспроизводящим запуском; это несогласованность предлагаемого порядка владельцев, обнаруженная при чтении до тестов.

**Решение пользователя, working model:** включить в D6 общую границу после каждого simulation step. Пользователь явно согласовал это расширение и его реализацию. В существующий Scheduling добавить `ScheduleStepDispatchedEvent` с `TickContext` и источником времени. `SubscriptionTickSource.Dispatch` публикует его после callback и завершения отложенных изменений подписок, до следующего шага; общий источник используется Realtime, TurnBased и Calendar. Существующий GameRuntimeHost на своей границе runtime подписывается/отписывается и исполняет уже имеющийся порядок Movement Pump → Skills Pump по этому событию. Обработка Skills завершается до следующего Dispatch, поэтому CapabilityHost получает последующие шаги после появления защиты. Scheduling передаёт общее уведомление и не вызывает конкретные сервисы механик. Существующую фазу AfterScheduleDispatch и её перечисленных потребителей сохранить. Для исполнения без Unity-host сохранить существующие публичные MovementService.PumpRuntime и SkillService.PumpRuntime: внешний драйвер вызывает их по тому же ScheduleStepDispatchedEvent, перед следующим шагом. Отдельный headless-менеджер или тестовый runtime-режим не добавлять. После подключения границы удалить ставший ненужным перенос backlog между записями Entity в Skills; не сохранять локальное воспроизведение чужих часов.

**Existing System Fit:** Scheduling владеет рассылкой времени; GameRuntimeHost — порядком вызова сервисов; CapabilityHost — сроками живых модификаторов и tags своих hosts; Skills — своими execution/carrier и tags carrier; Movement — разрешением pending traffic. EventBus используется для общего уведомления. Нового менеджера времени, нового DamageExecutor или привязки Skills к AIBrain не создавать. GameFlow/Drops/materialization/Knowledge не переводить на другую фазу.

**Best Practices:** сохранить координацию сервисов в существующей точке композиции, а в Scheduling — только общую границу рассылки. Этот принцип уже применён в `GameRuntimeHost.PumpRuntime` и разделении фаз `DeferredRuntimeWorkQueue`: отложенная работа выполняется на объявленной границе, а общий механизм не получает зависимость от конкретной механики. Новая граница нужна между отдельными simulation steps, поэтому существующую границу всей пачки не переименовывать и не менять скрытно.

Изменение Scheduling отдельно согласовано по правилу 11 PROJECT_RULES.md.

### D6: начальная ориентация и третье измерение снарядов — согласовано и внесено

**Verified, чтение исходников:** `Projectile.SetDirection` применяет `newRotation`, когда включён FaceDirection. В используемых DaggerProjectile, TurretKettleProjectile, BugPurpleProjectile и LightningBoltProjectile включён FaceDirection, выключен FaceMovement. `ProjectileWeapon.SpawnProjectile` передаёт поворот оружия; `DistantWeapon.SetupProjectile` для неподвижного снаряда возвращает Quaternion.identity. В новом `TrySpawnSkillCarriers` создаётся только позиция: Spatial даёт новой Entity единичный поворот, target-velocity задаёт скорость, но не поворот. Существующий WorldProjectionTarget уже применяет Spatial rotation; InteractionGeometry использует тот же rotation. Отдельного общего исполнителя ориентации для carrier нет.

**Verified до изменения, исходные данные:** DaggerProjectile использует BoxCollider2D 1.1220347 × 0.5 со смещением X=0.012440622; TurretKettleProjectile — BoxCollider2D 0.5 × 0.5. В текущих перенесённых box bindings третье измерение Y=0. Это ещё не завершённый перенос в объёмную 3D-форму, требуемую пунктом геометрии ReworkDisposition. У исходного Collider2D нет значения толщины; её нельзя извлечь из исходника. Sphere bindings уже имеют радиус во всех трёх измерениях. Причина runtime-ошибки не устанавливалась: эти различия выявлены чтением, без запуска.

**Решение пользователя, working model; оба пункта явно согласованы:**
1. В существующий `SkillCarrierSpawnResolverData` добавить явный режим начальной ориентации `Authored / SourceEntity / InitialVelocity` и authored rotation offset. Authored задаёт постоянный поворот; SourceEntity использует поворот Entity источника появления; InitialVelocity ориентирует локальную +Z по рассчитанной начальной скорости, затем применяет offset. Пространственная цель остаётся Entity. Нулевая скорость в режиме InitialVelocity — ошибка конфигурации; для неподвижной молнии явно задаётся Authored. Поворот вычисляется один раз после параметров скорости, перед регистрацией geometry, pose binding и Projection. Трёхмерный up берётся из уже разрешённого NavigationFrame; для строго вертикальной скорости roll определяется его Forward. Постоянное доворачивание в полёте не добавлять: в используемых исходниках FaceMovement выключен. Обновляемая локальная поза привязанного carrier остаётся независимым уже согласованным контрактом.
2. Явно задать толщину box в игровых assets: предлагается Dagger 1.122 × 0.5 × 0.5 и TurretKettle 0.5 × 0.5 × 0.5 в текущем масштабе; исходные длина/ширина и offset сохраняются. Для исходной продольной оси +X согласование с направлением InitialVelocity выполнено общей поправкой rotationOffset=(0,−90,0). Она поворачивает и форму, и существующее представление; отдельный поворот дочернего prefab не требуется. Это игровые параметры, а не автоматическое правило расширения любой 2D-формы.

**Existing System Fit:** SpawnResolver/Skills владеют начальной позой и параметрами carrier; Spatial остаётся единственным владельцем записи мировой позы; InteractionGeometry использует pose Entity для формы; существующий Projection применяет тот же pose к представлению. AIBrain выбирает Entity и не рассчитывает геометрию снаряда. Изменить `Skills/SkillCarrierContracts.cs`, `Skills/InMemorySkillRuntime.cs` и соответствующие Attack/Projection assets. Новый сервис ориентации, новый тип цели и игровая C#-ветка не нужны.

**Best Practices:** использовать единственную pose Entity для коллизии и представления; этот контракт уже реализован в `InteractionGeometryService.TryBuildSnapshot`, `ProjectionServiceCore.TryCreateSpawnRequest` и `WorldProjectionTarget.TryApplyPose`. Ориентацию нельзя реализовать только в визуальном prefab: тогда длинная форма и изображение имели бы разные направления. Толщина остаётся явно заданным параметром контента, как существующие `InteractionGeometryBindingData.Usage.CellSize`; общий query не достраивает размеры.

**Внесено после согласования:** SkillCarrierSpawnRotationType и RotationOffset добавлены в существующий SpawnResolver. Подтверждение materialization отмечает output, а commit yield добавляет его в окончательный результат один раз по order/yield/output identity. Смерть committed Entity не вычитает историю. Full закрывается успешно при выполнении объёма; временные препятствия сохраняют назначение. Partial после полного прохода закрывает admission и ждёт settlement принятых заказов; допустим нулевой результат. Snapshot содержит requested/confirmed, state, shortfall/failure. Cancel не объявляет завершение до окончания компенсации и освобождения materialization.

**Agent. Переписать** существующий ProductionAgentWork, удалить ProductionReleaseAgentWork. Лимит работы фиксируется при admission и не увеличивается из-за последующих смертей. Работа закрывает дальнейшее планирование, когда набран предел или завершён partial-проход, но продолжает наблюдать принятые orders. `BlocksPlanningAfterWorkSetCompletes` не должен разрешать новую партию после достижения лимита. Population пользуется тем же Production результатом; coverage/count Objective продолжает отдельно наблюдать фактический мир.

**Objective. Удалить** ObjectiveProductionReleasePlugin/condition/bindings и специальные release-ветки extraction по P4. **Оставить** накопительный ProductionYield без изменения смысла. Конкретная предлагаемая замена — существующий ExternalFactState, наблюдающий результат текущей попытки через Orchestration binding; не переносить создание операции в другой Objective plugin.

Согласованное ограниченное изменение общего ExternalFactState:

1. В Orchestration config задать binding `authored fact key → требование конечного выпуска`: content/form/tags, participant recipient и состояние результата. Producer/Agent и объём в condition не задавать.
2. `ObjectiveOrchestrationFactContainer` через projector такого binding извлекает требуемый Production release query **без ReleaseId**. Текущий projector, требующий уже зарегистрированную операцию из Objective, удалить. Декомпозиция выбирает Agent и способ выпуска; до его admission Production operation не существует.
3. При admission endpoint запрашивает Production identity и связывает её с `(RuntimeDomainId, ObjectiveRuntimeId, node id, activation generation, fact key)`. Пользователь явно согласовал включение RuntimeDomainId: ObjectiveRuntimeId уникален только внутри domain, его нумерация не меняется. Generation хранится в runtime узла и меняется при Reset/новой активации; authored assets не меняются. Production хранит выпуск, Orchestration — эту связь и наблюдение.
4. ExternalFactState registry/plugin разрешают факт по этому scope. Удалить применение глобального одного значения `string key` к таким bindings. В событии изменения передавать scope; добавить адресное удаление scope при detach. Прежнее глобальное хранение по одной строке заменить scoped хранением и обновить потребителей/fixtures; режим совместимости и fallback на global не добавлять. В просмотренном package публикации в этот registry найдены в тестах, а готового runtime-поставщика производственного результата нет.
5. Orchestration listener читает Production snapshot и публикует факт: full — подтверждён весь объём; partial — admission закрыт и принятая часть завершена. Failure/cancel не публикуют success. Во время отсутствия admitted operation факт unsatisfied, а не ошибка чтения.
6. Reset закрывает старый endpoint, который закрывает старый Production release и ждёт его cleanup; новая activation имеет новую generation/ReleaseId. Поздний результат старой операции не совпадает со scope новой. Objective только снимает своё наблюдение и не управляет заказами.

**Изменить:** ProductionRuntime/Service release routing; ProductionAgentWork/Population; release query/decomp; generic ExternalFactState scope и Objective node generation; Orchestration binding/projector/listener. Последний набор — согласованное изменение общего Objective-контракта; включение RuntimeDomainId дополнительно явно подтверждено пользователем. Без него scoped наблюдение нельзя честно назвать реализуемым только assets. Cooldown D13 от этого набора не зависит и Objectives не изменяет.

## D13. Cooldown ProductionCatalogData

**Согласованный working model:** настройки в самом каталоге; часы у пары `(domain, producer Entity, catalog)`. `ProductionData.supportedCatalogs` остаётся списком ссылок. Один catalog asset у двух бараков не объединяет их часы.

**Добавить поля в ProductionCatalogData:** явное включение cooldown, initial elapsed либо явно ready-at-start, числовой порог constant/LongProgressionData и его Economy source owner/resource/Absolute–Relative scale. Зависимость от PopulationProgressData не добавлять. Конфликт одновременно заданных initial elapsed и ready-at-start — ошибка authoring, не автоматический выбор. Для ready-at-start начальное накопление берётся из разрешённого порога при регистрации; дальше изменение порога не переписывает накопленное время.

**Runtime пары:** elapsed, последняя обработанная simulation-позиция, разрешённый порог, readiness version, необязательное право первого использования без подтверждённого output. Начало накопления — регистрация producer; состояние всех его поддерживаемых каталогов создаётся тогда же, а не при первом выборе каталога. В принятом order сохранить identity каталога admission: последующая смена current catalog не меняет владельца cooldown уже принятого заказа. **Runtime операции/пары:** использована ли пара, подтверждался ли первый output, принятые orders и состояние закрытия. Обычная операция имеет identity ProductionOrderId; группа — ProductionReleaseId. Таблица использований служит dedup, а не блокировкой до завершения всей группы.

| Событие | Переход |
|---|---|
| Read readiness | Вернуть состояние cooldown и причины неготовности без queue/ресурсных side effects |
| Первый заказ независимой операции | Проверить cooldown и отсутствие занятого первого использования, затем остальные admission-условия; закрепить использование только вместе с успешным приёмом заказа |
| Cooldown не готов | Временный отказ до вставки в очередь и reservations; инициатор повторяет запрос после изменения зависимости |
| Нет ресурсов/места в очереди при первом заказе | Обычный отказ Production; незавершённого закрепления за отклонённым заказом не остаётся |
| Продолжение уже допущенного выпуска у этой пары | Не требовать нового cooldown; проверить открытый admission, остаток объёма и обычные производственные ограничения |
| Первое подтверждение любого output операции у пары | В TryConfirmOutput после проверки актуальной output identity один раз сбросить elapsed и снять право первого использования; не ждать подтверждения остальных outputs этого yield |
| Повторное/следующее подтверждение той же операции | Не менять часы; order/materialization lifecycle продолжается |
| Порог снова достигнут | Разрешить новую независимую операцию, даже если прежняя ещё выпускает другую категорию или ждёт settlement |
| Все заказы использования закрылись до первого output | Снять право первого использования; накопление не сбрасывать |
| Cancel/compensation после первого output | Не возвращать готовность и не менять время более нового использования; результат выпуска/компенсация учитываются отдельно |
| Progress изменил порог | Пересчитать threshold и readiness, сохранить elapsed; уже принятые orders не пересматривать |
| Смена catalog или recipient | Не обнулять часы пары; для другого catalog использовать его собственную запись |

Для outputs без внешней materialization-подтверждаемости вызвать тот же однократный переход в точке, где Production подтверждает их автоматически перед commit; не ждать отсутствующего вызова TryConfirmOutput.

Clock работает по production simulation schedule и останавливается на pause. Порог 0 означает отсутствие временного ожидания, но первое использование до появления output всё равно имеет одного владельца; отдельно выключенный cooldown не ограничивает admission. Ошибку разрешения threshold/owner/resource не считать готовностью.

**Обычный многоцикловый и бесконечный заказ:** проверять cooldown при единственном admission заказа, сбрасывать один раз по его первому output. Его последующие yields продолжаются по существующим workDuration/recoveryDuration; не превращать их в повторные заказы. Бесконечный RequestedYields не допускается в конечную Release-группу; самостоятельный бесконечный заказ остаётся допустимым по прежним правилам reservation/input bindings. Истечение cooldown не обещает свободной линии: обычные ограничения производителя продолжают действовать.

**Read API:** добавить отдельное чтение catalog readiness в Production owner/service. `TryProbeStart` оставить составной проверкой возможности начать рецепт: он также проверяет очередь, линии и ресурсы, поэтому его false нельзя использовать как признак cooldown. `PopulationContentAvailabilitySession` читает только catalog readiness перед распределением. Временная занятость producer не исключает уже закреплённую категорию.

**Notifications:** включить readiness/version в производственное наблюдение и сравнение состояния; сейчас `ProductionSnapshotsEqual` этих данных не содержит. Изменения schedule threshold, Economy threshold и освобождение первого использования публикуют dependency change. PopulationProductionInvalidation пробуждает обычную применимость. Не добавлять Population clock или специальную ветку Orchestration для Population availability.

**Cleanup:** использовать terminal order/release callback после compensation для удаления operation-use записей; поздние подтверждения отклонять существующей проверкой output/order lifecycle до cooldown. Пока группа открыта, её dedup-запись сохраняется даже после истечения cooldown. Удаление producer/domain снимает часы и threshold watches; новый Entity id получает новое состояние. При закрытии Activity сначала закрыть admission, затем завершить/скомпенсировать orders, затем освободить записи.

**Assets:** Gold без cooldown; Unit 8 s, HeroSkill 6 s, Buff 5 s, Heal 15 s; все изначально готовы. При используемом 30 Hz это 240/180/150/450 simulation steps. `workDuration/recoveryDuration` строк recipes оставить; у Board recipes recovery = 0. Полнота/доли/объём остаются Population. **Удалить** все классы, поля и пять availability assets по R12/R13.

5. Только после полной реализации сообщить о готовности и ждать явного разрешения на проверки. Выполнить согласованный набор проверок один раз по итоговому изменению; повторять только затронутые проверки после обнаруженных и исправленных проблем, в пределах разрешения пользователя.

Приёмка остаётся из исходного плана: full/partial и нулевой выпуск; бюджеты в одну операцию; конкурирующие назначения и incoming; reset/cancel/compensation; пересечение порогов и сигналы; cooldown и независимые бараки; детерминизм состава; цепочки 1..16 и однократность Gold; существующие/будущие баффы; бой, защита, смерть, опыт; повторное открытие Activity; ссылки, нагрузка и пулы.
