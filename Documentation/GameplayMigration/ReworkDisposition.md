**Обязательные ограничения:** цель всегда Entity; геометрия framework — 3D. Координаты являются данными Entity. Не вводить Position-target, отдельную 2D-ветку или скрытое обнуление одного измерения. **Решение пользователя по SkillSpeed — working model, уточнён 2026-09-22:** усиление на 20% увеличивает скорость Rate на 20%, а не уменьшает задержку на 20%. Складываемые усиления суммируются: Rate = baseRate × (1 + сумма усилений). При baseRate = 1 один бонус 20% даёт Rate 1,2 и задержку 1 / 1,2 ≈ 0,833 секунды для базы 1 секунда; два таких бонуса дают Rate 1,4 и задержку ≈ 0,714 секунды до округления. Положительная длительность не становится нулевой или отрицательной. Новый переключатель Rate/Duration удалить; использовать существующий Rate. Изменение численного эффекта прежних бонусов уменьшения задержки согласовано. Новые значения контента задать явным authoring, без автоматической конвертации в runtime.

**Решение пользователя по отбрасыванию — working model текущей версии:** удалить добавленную реализацию отбрасывания и все её подключения без замены. Новый интеграционный контур в этой версии работает без отбрасывания, реакции на массу и передачи толчка соседним объектам. Интеграция полноценной 3D-физики — отдельная будущая задача; библиотеку и контракт интеграции согласовать в ней. Не оставлять заглушки эффектов, неиспользуемые force API или параметры «на будущее». Исходный старый игровой путь и его физику не менять; исходные параметры сохранить в реестре как справочные данные.

**Решение по cooldown — working model для переделки:** настройки размещать внутри самого ProductionCatalogData; состояние и отсчёт хранить в ProductionRuntime отдельно для каждой пары производитель Entity + каталог. ### P6. Cooldown каталогов в Production

**Working model:** cooldown определяет готовность конкретного производителя использовать каталог в следующей операции. Настройки принадлежат catalog asset; таймер принадлежит паре производитель Entity + каталог в ProductionRuntime его domain. Заказы одного заполнения доски принадлежат одному выпуску и могут использовать несколько recipes и producers; у каждого участвующего производителя собственный таймер каталога. Production не получает зависимости от Board, Population или игровых названий категорий.

**Задать внутри самого ProductionCatalogData:**

- Порог cooldown через существующую LongProgressionData.
- Источник аргумента: ресурс Economy, привязку владельца и wallet, шкалу Absolute/Relative и её основание.
- Начальное накопленное время — явно в данных. Длительности исполняются в шагах выбранной simulation; пауза останавливает отсчёт.

**Оставить** ProductionData.supportedCatalogs списком ссылок на ProductionCatalogData. **Не добавлять** тип-обёртку «ProductionCatalogData + cooldown», настройки cooldown на каждой ссылке ProductionData, режим общего таймера или группировку производителей. Параметры заполняет автор контента в Inspector каталога либо явной authoring-командой; игрок их не заполняет. При реализации переноса настроить пять используемых catalog assets по согласованным значениям.

**Оставить** workDuration и recoveryDuration внутри ProductionCatalogEntryData: это длительность работы и восстановление производственной линии после каждого yield конкретного рецепта. Дополнительный cooldown каталога включать явно его настройками. Для каталогов без этого ограничения сохранить обычные очереди, workDuration и recoveryDuration. У производителей клеток recoveryDuration оставить нулевым; 15 секунд Heal задавать cooldown каталога, иначе пауза возникнет между отдельными клетками одного заполнения.

Прогрессия объёма остаётся на PopulationAgentData. Прогрессия cooldown возвращает длительность; общий прогресс забега обе системы читают из Economy. Authored assets во время игры не менять. Для Heal задать постоянный порог 15 секунд simulation; начальную готовность перенести из явных настроек текущего HealContentAvailability.asset. Остальные значения перенести из четырёх соответствующих availability assets явным authoring, затем удалить эти пять assets и их ссылки.

**Хранить состояние в ProductionRuntime** конкретного domain отдельно для каждой пары производитель Entity + каталог. Два барака с одним catalog asset используют одинаковые параметры и независимые таймеры. Смена получателя не создаёт новую готовность у того же производителя. Состояние сохраняется между назначениями Population и переключениями каталога у живого производителя; смена каталога не должна сбрасывать его таймер. Несколько незавершённых операций могут использовать пару последовательно по её готовности; единственного владельца каталога до завершения всего выпуска не вводить.
